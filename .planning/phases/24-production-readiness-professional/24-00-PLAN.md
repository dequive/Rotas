# Phase 24: Production Readiness Professional

## Objective

Elevar o ROTAS de MVP avancado / pre-producao para um grau de producao
profissional serio, com contratos estaveis, seguranca consistente, modulos
completos, qualidade de codigo verificavel, testes automatizados conclusivos,
observabilidade operacional e processo de release controlado.

Esta fase nao adiciona novas funcionalidades comerciais por si so. O foco e
fechar lacunas que impedem operacao real com clientes, motoristas, frota,
cobranca, documentos, combustivel e oficina sem risco excessivo.

## Current Technical Verdict

Estado actual identificado em auditoria tecnica:

- O backend tem arquitectura modular, RLS, auth, auditoria, idempotencia,
  storage local/R2, jobs, metricas e muitos dominios reais.
- O Manager e a PWA Driver fazem typecheck e build, mas ainda ha quebras de
  contrato e ausencia de E2E de fluxos reais.
- A CI backend nao esta verde porque `ruff check app tests` falha.
- A PWA motorista usa endpoints de dashboard que exigem roles de gestor.
- A autorizacao e inconsistente em alguns modulos, especialmente `clients`.
- Existem services demasiado grandes em `billing`, `trips`, `workshop`,
  `cargo` e `fuel`.
- Existem duas configuracoes Railway concorrentes.
- Ha artefactos locais de upload no working tree que nao devem fazer parte da
  disciplina de release.

## Production Readiness Gates

O sistema so pode ser considerado pronto para producao profissional seria quando
todos estes gates estiverem fechados:

| Gate | Nome | Criterio minimo |
| --- | --- | --- |
| G0 | Baseline limpo | Working tree de release sem artefactos locais, configs duplicadas resolvidas |
| G1 | CI verde | Ruff, pytest completo, typecheck e builds passam em CI |
| G2 | Contratos API | Backend, Manager e Driver usam o mesmo envelope de erro e schemas versionados |
| G3 | Driver PWA real | PWA usa apenas endpoints driver_app ou sync dedicados, sem depender de dashboard |
| G4 | RBAC consistente | Todas as rotas mutaveis exigem permissao explicita e tests de negacao |
| G5 | Dominios criticos fechados | Viagens, carga, cobranca, combustivel e oficina tem invariantes testadas |
| G6 | Observabilidade | Logs, metricas, Sentry e health checks cobrem API, jobs, sync e storage |
| G7 | Release operacional | Migrations, rollback, seed, backup e smoke tests documentados |
| G8 | Piloto controlado | Fluxos ponta-a-ponta executados com dados reais simulados e criterios aceites |

## Implementation Roadmap

### Track A: Baseline, CI and Release Hygiene

Priority: P0

Objective: garantir que a base esta verificavel e que nenhum release ocorre com
estado ambiguo.

Tasks:

1. Resolver configuracao Railway duplicada.
   - Manter uma fonte de verdade para backend deploy.
   - Decidir se o deploy parte da raiz ou de `backend/`.
   - Confirmar comando final de start: `gunicorn ... app.main:app` ou equivalente.
   - Confirmar `preDeployCommand` com Alembic e URL correcta.

2. Limpar artefactos locais.
   - Garantir que `backend/.rotas_uploads/`, `dist/`, `.next/`, caches e `.env`
     nao entram em git.
   - Mover exemplos de uploads para fixtures quando forem necessarios a testes.

3. Fazer lint backend ficar verde.
   - Corrigir `ruff check app tests`.
   - Corrigir B008 usando `Annotated[..., Query(...)]` e `Annotated[..., Depends(...)]`.
   - Corrigir imports, `zip(strict=...)`, excecoes `raise ... from exc`,
     variaveis nao usadas e linhas longas.

4. Executar pytest completo em CI e local.
   - Garantir que a suite completa conclui.
   - Separar testes lentos/integracao com markers.
   - Remover skips permanentes ou justificar com issue/plano.

5. Formalizar smoke test de release.
   - `/health`, `/health/deep`, `/version`.
   - Login dashboard.
   - Pairing driver.
   - Criar viagem.
   - Sync offline batch.
   - Emitir documento de cobranca.
   - Export/download de ficheiro.

Acceptance criteria:

- `python -m ruff check app tests` passa.
- `python -m pytest -q --tb=short` passa em CI.
- `npm --workspace apps/manager run build` passa.
- `npm --workspace apps/driver run build` passa.
- Existe apenas uma configuracao Railway activa.
- `git status --short` de release nao mostra artefactos de runtime.

### Track B: API Contracts and Error Envelope

Priority: P0

Objective: estabilizar o contrato entre backend, Manager e Driver PWA.

Tasks:

1. Definir envelope unico de erro.
   - Backend actual: `{"error": {"code", "message", "details", "request_id"}}`.
   - Manager e Driver devem ler este envelope em todos os clients.
   - Manter fallback para `detail` durante transicao.

2. Criar cliente API comum no Manager.
   - Remover chamadas directas duplicadas a `NEXT_PUBLIC_API_URL`.
   - Preferir API routes server-side quando for necessario usar cookies httpOnly.
   - Padronizar retry de refresh token.

3. Criar cliente API robusto na PWA Driver.
   - `request()` deve tratar `error.code`.
   - Sync deve usar refresh token ou uma funcao autenticada comum.
   - Erros de revogacao, sessao expirada e conflito devem ter estados UI.

4. Documentar contratos criticos.
   - Auth login/refresh/MFA.
   - Driver pairing.
   - Driver bootstrap.
   - Sync batch.
   - Files upload.
   - Billing issue/export/payment.

Acceptance criteria:

- Nenhum frontend depende exclusivamente de `body.detail`.
- Testes cobrem erro `driver_access_revoked`, `invalid_refresh_token`,
  `idempotency_key_reused`, `forbidden` e `tenant_mismatch`.
- OpenAPI reflecte schemas de resposta para endpoints criticos.

### Track C: Driver PWA Production Contract

Priority: P0

Objective: garantir que a PWA motorista funciona em campo com token
`driver_app`, offline-first e sem depender de endpoints de gestor.

Tasks:

1. Criar endpoints driver-app dedicados.
   - `GET /api/v1/driver/bootstrap`
   - `GET /api/v1/driver/active-trip`
   - `GET /api/v1/driver/checklist-templates`
   - `POST /api/v1/driver/trips` se a politica permitir motorista criar viagem.
   - `GET /api/v1/driver/profile`

2. Rever autorizacao.
   - Estes endpoints devem aceitar `driver_app`.
   - Devem restringir dados ao `driver_id` do token.
   - Nunca devem permitir leitura geral de frota/clientes/motoristas.

3. Ajustar PWA.
   - Remover uso de `/api/v1/trips`, `/api/v1/vehicles`, `/api/v1/drivers` e
     `/api/v1/checklist-templates` quando autenticado como motorista.
   - Usar bootstrap driver dedicado.
   - Persistir active trip e templates localmente.

4. Corrigir sync de token.
   - `processSyncQueue` deve renovar access token em 401.
   - Sync deve parar em `driver_access_revoked` sem apagar dados locais.
   - Sync deve distinguir conflito de falha temporaria.

5. Offline proof hardening.
   - Comprimir fotos antes de upload.
   - Guardar timestamp, device_id, local_id e, quando disponivel, GPS.
   - Suportar retry de upload independente do retry do batch.

Acceptance criteria:

- PWA consegue pair, bootstrap, criar/registar fluxo, ficar offline, voltar online
  e sincronizar sem token dashboard.
- Teste API prova que token driver_app recebe 200 nos endpoints driver e 403 nos
  endpoints dashboard.
- Teste E2E simula fila offline com pelo menos: checklist, fuel_log, load_permit,
  manifest, stop e delivery_proof.

### Track D: RBAC and Permission Model

Priority: P0

Objective: substituir roles genericas insuficientes por permissoes consistentes
por dominio e acao.

Tasks:

1. Definir matriz de permissoes.
   - `fleet.read`, `fleet.write`
   - `drivers.read`, `drivers.write`, `drivers.pairing`
   - `trips.read`, `trips.dispatch`, `trips.close`
   - `cargo.write`, `cargo.validate_delivery`
   - `billing.read`, `billing.write`, `billing.issue`, `billing.void_payment`
   - `fuel.read`, `fuel.write`, `fuel.approve_adjustment`
   - `workshop.read`, `workshop.write`, `workshop.release_vehicle`
   - `admin.users`, `admin.tenant`, `audit.read`

2. Corrigir modulos sem RBAC completo.
   - `clients`: aplicar read/write roles e testes viewer.
   - Rever `mechanic` em `DASHBOARD_ROLES`.
   - Rever leitura de billing por mechanic/viewer.

3. Criar helper de permissao.
   - `require_permissions(...)` ou evolucao de `require_roles`.
   - Manter compatibilidade temporaria com roles actuais.

4. Testar negacao.
   - Para cada dominio critico, testar viewer/mechanic/manager/admin.
   - Testar driver_app rejeitado em dashboard.

Acceptance criteria:

- Nenhuma rota mutavel usa apenas `get_current_principal`.
- Cada router declara permissao explicita.
- Existe matriz documentada e testada.
- Testes de cross-tenant e forbidden passam.

### Track E: Domain Hardening by Module

Priority: P1

Objective: fechar invariantes de dominio e reduzir risco operacional/financeiro.

#### E1: Trips and Dispatch

Tasks:

- Centralizar state machine de viagem.
- Validar uma viagem activa por motorista/viatura salvo waiver aprovado.
- Usar travas transacionais em start/dispatch/complete/close.
- Garantir que `complete` e `close` verificam documentos, custos, incidentes e
  waivers.
- Separar service grande em subservices: lifecycle, dispatch, events, costs,
  closeout.

Acceptance criteria:

- Testes cobrem transicoes invalidas.
- Testes cobrem concorrencia para mesma viatura/motorista.
- Fecho de viagem sem documentos obrigatorios retorna erro de dominio claro.

#### E2: Cargo and Documents

Tasks:

- Mover logica de negocio restante dos routers para services.
- Formalizar documentos obrigatorios por tipo de carga e tenant policy.
- Criar estados claros para documento: draft, submitted, validated, rejected,
  disputed, superseded.
- Versionar documentos reemitidos.
- Validar divergencia entre documento do cliente e prova submetida.

Acceptance criteria:

- Nenhum router de cargo faz commit directo.
- Documento rejeitado cria exception operacional.
- Documento substituido mantem trilha auditavel.

#### E3: Billing and Payments

Tasks:

- Separar `billing/service.py` em:
  - document_lifecycle
  - billing_generation
  - payments
  - allocations
  - exports
  - ar_reporting
- Introduzir ledger/audit financeiro imutavel para eventos financeiros.
- Garantir travas ou constraints para evitar pagamento/alocacao duplicada.
- Cobrir cancelamento, nota de credito/debito, recibo e invoice-receipt com
  invariantes financeiras.
- Validar que documentos fiscais cumprem requisitos legais aplicaveis.

Acceptance criteria:

- Pagamento concorrente nao duplica saldo nem alocacao.
- Documento emitido nao pode ser alterado sem nota/estorno apropriado.
- AR aging bate com pagamentos e voids.
- Tests de estado financeiro cobrem paid, overdue, cancelled, voided.

#### E4: Fuel

Tasks:

- Confirmar que `fuel_movements` e fonte de verdade de stock.
- Bloquear stock negativo em nivel service e database.
- Separar quem regista abastecimento de quem aprova ajuste.
- Associar custo medio ponderado ao custo real da viagem.
- Criar exceptions para divergencias acima de tolerancia.

Acceptance criteria:

- Teste concorrente de duas saidas do mesmo tanque nao deixa stock negativo.
- Compra nao aumenta stock sem recepcao verificada.
- Ajuste exige permissao, motivo e auditoria.

#### E5: Workshop

Tasks:

- Separar `workshop/service.py` em subdominios:
  - maintenance_requests
  - work_orders
  - tasks_labor
  - spare_parts_inventory
  - tools_checkouts
  - maintenance_plans
  - calibrations
  - installed_parts
- Garantir que work order activa afecta disponibilidade da viatura.
- Bloquear checkout de ferramenta critica com calibracao vencida.
- Garantir que instalacao de peca seriada muda estado e historico.
- Definir regra de release operacional da viatura.

Acceptance criteria:

- Service principal deixa de concentrar todas as regras.
- Testes cobrem disponibilidade durante manutencao.
- Testes cobrem peca seriada instalada/removida.
- Testes cobrem ferramenta critica vencida.

  - criar cliente

### Track G: Observability and Operations

Priority: P1

Objective: permitir operar, diagnosticar e recuperar o sistema em producao.

Tasks:

- Logs estruturados com request_id, tenant_id, user_id, driver_id quando aplicavel.
- Metrics por endpoint, status, latencia, sync batch size, upload failure,
  job failure, Redis unavailable, DB pool.
- Sentry com scrub de PII no backend, Manager e Driver.
- Heartbeat de ARQ worker.
- Dashboard operacional minimo:
  - erro 5xx por modulo
  - tamanho de filas
  - jobs falhados
  - sync conflicts
  - uploads falhados
- Runbooks:
  - DB migration failed
  - Redis unavailable
  - R2 unavailable
  - ARQ worker down
  - sync conflict spike
  - rollback release

Acceptance criteria:

- `/health/deep` detecta DB, Redis e worker.
- Falha de R2 gera erro rastreavel sem perder auditoria.
- Runbook de rollback testado em staging.

- Adicionar hashing/checksum para documentos gerados.

Acceptance criteria:

## Risk Register

| Risco | Impacto | Mitigacao |
| --- | --- | --- |
| PWA motorista dependente de endpoints dashboard | Operacao de campo falha | Endpoints driver dedicados e E2E offline |
| Lint/CI vermelho | Release sem qualidade verificavel | Corrigir Ruff e tornar CI bloqueante |
| RBAC inconsistente | Acesso indevido a dados/acoes | Matriz de permissoes e testes forbidden |
| Billing sem ledger forte | Erros financeiros e auditoria fraca | Ledger/audit financeiro imutavel |
| Services gigantes | Regressao e manutencao dificil | Dividir por subdominios |
| Deploy config duplicado | Release sobe comando errado | Fonte unica Railway |
| Artefactos locais no repo | Vazamento/dificuldade de release | Gitignore, limpeza e storage externo |
| Falta E2E offline | Bugs no campo | Testes offline/online com Playwright/Vite |
